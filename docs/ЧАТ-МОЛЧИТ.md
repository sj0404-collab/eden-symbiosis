# Почему чат отвечал один раз, а потом молчал

Жалоба: *«работает один раз, потом молчит, нужно перефразировать — снова работает,
молчит, и снова работает; дальше первого раунда не доходит»*.

Это не одна поломка, а пять, и они складывались так, что выглядели как одна.
Ниже — каждая: что происходило, где именно, и чем это лечится.

---

## 1. Обрезка истории разрывала пару «вызов инструмента → результат»

**Главная причина того самого «через раз».**

Когда модель вызывает инструмент, в истории появляется пара сообщений:

```
assistant  tool_calls: [ {id: "call_7", ...} ]
tool       tool_call_id: "call_7", content: "..."
```

Перед каждым запросом бралось последние 25 сообщений:

```js
history.slice(-CONFIG.maxHistory)
```

Срез не знает про пары. Как только разговор становился длиннее окна, край среза
рано или поздно проходил **между** этими двумя сообщениями. Оставался `tool` без
своего `assistant` — и OpenAI-совместимый API (OpenRouter, GitHub Models) отвечает
на такое не текстом, а ошибкой:

```
HTTP 400: messages with role 'tool' must be a response to a preceding
message with 'tool_calls'
```

Тот же разрыв возникал, если запуск падал прямо во время инструмента: `tool_calls`
оставались в истории, а результаты к ним — нет.

Отсюда и «перефразируй — заработает»: другая длина сообщения сдвигала окно, битая
пара выпадала за край, и ответы возвращались. До следующего вызова инструмента.

**Исправление** — `repairToolPairs()` в `agent/zen-agent.js`: перед отправкой из окна
убираются `tool` без своего вызова и `tool_calls` без результатов. Текст ассистента
при этом сохраняется, теряется только висящая половина.

**Доказано** — `tests/t_chat_history.js` гоняет 24 раунда через локальный сервер,
который проверяет окно так же строго, как настоящий API. На старом коде:

```
round 12  FAIL  HTTP 400 ... Offending id: call_3b
round 15  FAIL  HTTP 400 ... Offending id: call_6a
round 16  FAIL  ...
       ↳ the chat went quiet from round 12 onward
```

То есть буквально: работает, молчит, работает, молчит. После правки — 24 из 24.

---

## 2. Страница не понимала, что запуск упал

Сервер помечает неудачный запуск статусом `error`. Страница ждала:

```js
['completed','failed','aborted'].includes(run.status)
```

`error` в списке нет. Упавший запуск опрашивался **бесконечно**: кнопка оставалась
квадратом «стоп», статус — «думает», ошибка не печаталась никогда. Со стороны
телефона это неотличимо от зависания.

**Исправление** — сервер теперь присылает явный флаг `done`, а страница спрашивает
`runIsOver(run)`, который на него смотрит (и умеет откатиться на список «живых»
статусов для старого агента). Плюс:

- ответ `404` на запуск (агент перезапустили) завершает опрос с внятным текстом,
  а не крутится вечно;
- ~33 секунды подряд неудачных опросов — сообщение о потере связи;
- `endRun()` идемпотентна, поэтому ответ не печатается по два раза.

---

## 3. Новый запуск успевали убить как «зависший»

`POST /api/agent/run` сначала подчищает «протухшие» запуски. Признаком служил
`agentBusy` — но флаг поднимался **на тик позже**, чем появлялся объект запуска:

```js
HUB_WEB_RUNS.set(run.id, run);
setImmediate(async () => { ... agentBusy = true ... });   // ← окно
```

Сообщение, попавшее в это окно, видело запуск в статусе `queued` без владельца,
объявляло его мёртвым и помечало ошибкой — **а агент продолжал над ним работать**.
Вкладка опрашивала запуск, который сервер уже списал.

**Исправление** — агент занимается синхронно, до `setImmediate`; активный запуск
не трогается никогда; запуск моложе 5 секунд не считается протухшим. И флаг теперь
снимается ещё и в `launchWebRun`, иначе падение до входа в цикл оставляло агента
навсегда «занятым» — с ответом `409` на всё подряд до перезапуска процесса.

---

## 4. В браузере не работал повтор при сбое провайдера

Запасной путь для Zen стоял под условием:

```js
if (currentProvider === 'zen' && CONFIG.streamMode) res = await callZenWithRetry(...)
```

А `launchWebRun` выключает стриминг для каждого веб-запуска (`CONFIG.streamMode = false`).
Значит, **в браузере эта ветка не срабатывала ни разу**: первый же сбой бесплатной
модели — 500, обрыв, лимит — убивал задачу целиком. В терминале тот же сбой тихо
переключал модель и работа продолжалась. Поэтому CLI казался надёжным, а чат — нет.

**Исправление** — условие на `streamMode` убрано, повтор работает одинаково везде.

---

## 5. Пустой ответ модели уходил в никуда

Если модель дважды возвращала пустоту, цикл завершался с пустым `finalAnswer`.
Запуск помечался `completed` — успешно, без текста. Консоль не печатала ничего.

Отдельно: стриминговая ветка подставляет строку `«Модель вернула пустой ответ.»`
вместо пустого тела, и она проходила дальше как настоящий ответ модели.

**Исправление** — эта строка распознаётся как пустота; после двух пустых ответов
подряд пользователь получает текст с названием модели и причиной (обычно исчерпан
лимит бесплатной модели или слишком длинный контекст). Плюс служебная подсказка
модели больше не остаётся в истории — раньше она копилась там с каждым разом.

Ещё: `/api/agent/reset` не опускал `abortRequested`. Сброс, сделанный когда ничего
не выполнялось, оставлял флаг поднятым — и следующая задача умирала на нулевом шаге
с «Задача остановлена пользователем», что выглядит как игнор сообщения.

---

## Как проверить

```bash
node tests/t_chat_replies.js    # 40 проверок по исходникам
node tests/t_chat_history.js    # 24 раунда против строгого стенда
node tests/t_chat_live.js       # 7 сценариев через реальный HTTP API
```

Все три запускаются и в CI: `tools/run_tests.sh` подхватывает `tests/*.js`, а workflow
**Tests** теперь срабатывает на любые изменения в `agent/**` — раньше в списке путей
был только `agent/capabilities.js`, поэтому правки самого агента проезжали мимо тестов.

`t_chat_live.js` и `t_chat_history.js` поднимают настоящего агента и разговаривают с
ним по тому же HTTP API, что и телефон; ответы провайдера подменяются локальным
стендом, поэтому сеть и ключи не нужны. Логика завершения запуска берётся прямо из
`agent/hub/index.html`, а не переписывается в тесте — иначе сломанная страница
проходила бы зелёный набор, что ровно и произошло с багом №2.

Обратная проверка: на исходном коде `t_chat_replies.js` даёт 25 падений,
`t_chat_history.js` — 7, `t_chat_live.js` — 1.
