# Два стола, без паролей

Linux и Windows, оба открываются ссылкой в браузере. Вводить нечего: пароля
нет ни у одного.

Запуск: панель → «Столы» → **Оба стола**. Через 3–5 минут в панели появляются
две плитки с живым превью. Отдельная страница — `desks.html`.

| | Linux | Windows |
|---|---|---|
| Что показывает | XFCE на Xtigervnc | собственный рабочий стол раннера (Windows Server 2025) |
| Как отдаётся | noVNC (VNC поверх WebSocket) | кадры GDI, MJPEG поверх HTTP |
| Аутентификация | тип 1 (None) — нечего предъявлять | нет вовсе, сервер её не умеет |
| Терминал | есть, `/term/` | PowerShell прямо на столе |
| Управление | мышь, клавиатура, тач | мышь, клавиатура, тач (SendInput) |
| Адрес | случайный `*.trycloudflare.com` | случайный `*.trycloudflare.com` |
| Живёт | до 6 часов | до 6 часов |

## Почему без пароля

Раньше Windows отдавался по RDP: адрес, логин, пароль. Он не заработал ни разу.
Клиент проходил TLS, лицензирование и настройку каналов, а потом получал
`LOGON_FAILED_UPDATE_PASSWORD` — «смените пароль», диалога для чего у RDP нет.
Учётная запись создавалась четырьмя разными способами (`New-LocalUser`,
`net user`, `AccountManagement.SetPassword`, ADSI `PasswordExpired`), политика
машины снималась через `net accounts /maxpwage:unlimited` — в логе всё
правильно, клиент отказывает.

Пароль убран целиком, вместе с ним — весь этот класс отказов. Оба стола теперь
обычные веб-страницы.

**Честная обратная сторона:** кто знает адрес, тот управляет столом. Адрес —
случайное имя на `trycloudflare.com`, публикуется в ветку `session-state`
(на публичном репозитории она публична) и перестаёт работать вместе с сессией,
максимум через шесть часов. На раннере лежит только копия этого репозитория и
`GITHUB_TOKEN`, ограниченный им же. Если так нельзя — сделайте репозиторий
приватным, всё продолжит работать.

## Почему Cloudflare, а не ngrok

Бесплатный ngrok даёт **один** туннель на аккаунт — двух столов одновременно
быть не может в принципе. Quick-туннели cloudflared не требуют ни аккаунта, ни
токена, и их можно поднять сколько угодно. Плата за это — адрес меняется каждый
раз, поэтому его читает панель, а не человек.

## Почему на Windows не VNC

TightVNC на раннере отдаёт **чёрный экран**. Это измерено, а не предположено —
три кадра одного и того же стола, снятые в одном прогоне с разницей в секунды:

```
GDI CopyFromScreen           26508 различных цветов   (настоящий стол)
TightVNC как служба              1 цвет               (чёрный)
TightVNC как приложение          1 цвет               (чёрный)
```

Отключение mirror-драйвера, `BlankScreen` и `RemoveWallpaper` ничего не
изменило. Сам стол в порядке — не работает путь захвата TightVNC на машине без
настоящего видеодрайвера. Поэтому Windows-стол построен на том пути, который
там доказанно работает: снимок GDI, отдаваемый как MJPEG.

Перед публикацией адреса шаг считает цвета в кадре и **роняет job**, если их
меньше трёх. Чёрный экран, выдающий себя за рабочую сессию, больше не пройдёт.

## Грабли, на которых это строилось

Всё измерено на живых раннерах, каждая строка — отдельный прогон.

1. **`Sorry, loopback connections are not enabled`.** Нужен `AllowLoopback=1`;
   `LoopbackOnly=1` только ограничивает подключения локальными, но не разрешает
   их. Отказ приходил на первом же рукопожатии и выглядел как проблема пароля.
2. **Обрезанный текст ошибки.** Проба читала 8 байт и показывала `Sor` —
   поэтому причину искали три круга. Отказ VNC: нулевой байт счётчика, затем
   4 байта длины, затем строка. Читать нужно целиком.
3. **`Start-Process` умирает вместе со своим шагом.** Три сервера запущены в
   одном шаге: `Start-Process` (6080), `cmd /c start` (6081), задача
   планировщика (6082). В следующем шаге 6080 мёртв, остальные живы. Именно
   так туннель оставался поднятым, а за ним ничего не было — снаружи это
   выглядело как 502.
4. **`cmd /c start` подвешивает шаг**, если процесс не завершается: pwsh ждёт
   закрытия дескрипторов. Сервер стола запускается задачей планировщика — и от
   имени вошедшего пользователя, не SYSTEM, иначе снимается пустая сессия 0.
5. **Python на Windows пишет в cp1252** и падает на «Стол Windows»:
   `UnicodeEncodeError`, файл пуст, шаг зелёный, адрес не опубликован.
   `publish_session.sh` теперь пишет байты UTF-8 напрямую.
6. **`push -f` стирал соседний стол.** Linux клонировал ветку до появления
   файла Windows и затирал его своим деревом. Теперь push обычный, с
   повтором поверх чужих изменений; каждый стол трогает только свой файл.
7. **Общий `/tmp/session.json`** — два одновременных вызова перемешивали
   данные. Теперь у каждого свой временный файл.
8. **Watchdog по PID ничего не ловит.** Мёртвый сервер за живым туннелем
   отвечает 502, а процесс туннеля жив. Сторож проверяет то, что видит
   посетитель, а не идентификатор процесса.

## Файлы

- `.github/workflows/desks.yml` — оба стола, по job на каждый
- `tools/win_desk_server.py` — сервер Windows-стола (GDI + MJPEG + SendInput)
- `tools/open_tunnel.sh` — quick-туннель cloudflared для Linux
- `tools/publish_session.sh` — публикует `session-linux.json` /
  `session-windows.json` в ветку `session-state`
- `docs/desks.html` — страница со столами
