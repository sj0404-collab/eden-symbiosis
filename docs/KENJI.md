# Eden + Kenji-NX: что выяснилось

Разведка перед работой. Всё ниже — проверено клонированием и чтением кода,
а не пересказ описаний.

## Это два несовместимых проекта

| | Eden | Kenji-NX |
|---|---|---|
| Происхождение | форк **yuzu** | форк **Ryujinx** |
| Язык | C++ | **C#** (3924 файла `.cs`) |
| Сборка | CMake + Android NDK | .NET 10 SDK + NativeAOT |
| Лицензия | GPL-3.0-or-later | MIT |
| Пакет Android | `dev.eden.eden_emulator` | `org.kenjinx.android` |

**Общего кода — ноль.** Это не два форка одного проекта, а две независимые
реализации одной консоли. «Слить исходники» в буквальном смысле нельзя: нет
файла, который можно было бы взять из одного и положить в другой. Ни один
патч из нашего `patch/` к Kenji не применим — там нет ни C++, ни тех классов.

Хорошая новость по лицензиям: MIT совместим с GPL-3.0 **в одну сторону** —
код Kenji можно включить в проект под GPL-3, но не наоборот.

## Как собирается Android-версия Kenji

`src/KenjinxAndroid/libkenjinx/build.gradle` запускает:

```
dotnet publish -r linux-bionic-arm64 -p:PublishAotUsingRuntimePack=true
               -p:DefineConstants=ANDROID
```

То есть C#-ядро компилируется NativeAOT в `libkenjinx.so`, а Kotlin-приложение
(`compileSdk 37`, `minSdk 29`) грузит его через JNI. Нужны .NET 10 SDK и
отдельный LLVM-тулчейн — ничего этого в нашем текущем `build.yml` нет.

Готового CI для Android у Kenji тоже нет: в `.github/workflows` только
десктопные сборки.

## Размеры: измерено, не оценено

Ядро Kenji собрано в наших Actions (`kenji-probe.yml`, прогон #2) —
`dotnet publish -r linux-bionic-arm64` с NativeAOT:

| | сырой | в APK (deflate) |
|---|---|---|
| `LibKenjinx.so` (Kenji) | **54.7 МБ** | **19.6 МБ** |
| `libyuzu-android.so` (Eden) | 34.4 МБ | 12.3 МБ |

Библиотека Kenji уже без отладочных символов (`.debug_info` и `.symtab`
отсутствуют) — ужимать нечего, это чистый код.

Текущий APK Eden — 41 МБ, но он debug: 22 МБ занимают `classes.dex` и
`classes15.dex`, которые лежат **без сжатия**. Если сжать, те же dex дают
9.2 МБ.

**Итог для одного APK с двумя ядрами:**

```
LibKenjinx.so                 19.6 МБ
libyuzu-android.so            12.3 МБ
dex Eden (сжатые)              9.2 МБ
Compose UI Kenji               ~3 МБ
ресурсы и прочее               ~3 МБ
------------------------------------
                             ~47 МБ
```

**Цель 25 МБ недостижима для двух ядер — превышение примерно вдвое.**
Для сравнения: один Eden в release укладывается примерно в 24 МБ, один
Kenji — примерно в 26 МБ. То есть 25 МБ хватает ровно на один движок, и то
впритык.

Уменьшить это можно только тремя способами, и все они меняют условие задачи:
скачивать второе ядро при первом запуске (APK маленький, но нужен интернет),
раздавать два APK, или согласиться примерно на 47 МБ.

## Хорошая новость: переключение движков технически простое

Ядро Kenji экспортирует **49 плоских C-функций**
(`[UnmanagedCallersOnly(EntryPoint = "device_load")]`, `graphics_initialize`,
`device_install_firmware` и так далее) и грузится обычным
`System.loadLibrary("kenjinxjni")`. То есть это ровно такая же нативная
библиотека, как у Eden — никакого .NET-рантайма в приложении, никакой Mono.

Значит, одна оболочка Symbiosis действительно может держать оба ядра и
переключаться между ними: два `.so`, два тонких Kotlin-слоя, общая папка
игр, ключей, прошивки и сейвов. Вопрос только в весе APK, не в архитектуре.

## Что реально означает «симбиоз»

Три разных вещи, и выбрать надо осознанно:

**А. Один APK, два движка.** Оболочка Symbiosis запускает Eden или Kenji на
выбор — для каждой игры тот, что её тянет. Технически честно: два `.so` в
одном APK, общая папка игр/ключей/прошивки/сейвов, единый выбор в интерфейсе.
Дорого: нужна сборка обоих ядер в CI (+ .NET 10 и LLVM), APK вырастет вдвое.

**Б. Два APK, общие данные и панель.** Собираем оба отдельно, но с общей
папкой данных, общим экраном настройки и переключением из панели. Заметно
дешевле, и большая часть уже есть.

**В. Только зеркало.** Кладём Kenji в репозиторий, чтобы он не исчез, и берём
из него идеи (у Ryujinx-линии другая модель памяти и свой шейдерный
транслятор), не пытаясь собирать.

## Риск, о котором надо сказать прямо

GitHub уже снял по DMCA релизы Kenji для Android. Если зеркалить его исходники
в публичный репозиторий на GitHub, тот же запрос может прилететь сюда — вместе
с этим репозиторием и, в худшем случае, аккаунтом. Варианты: приватный
репозиторий, или зеркало только в виде архива в релизе, или не зеркалить
вообще.

Ничего из этого я пока не сделал — жду решения.
